## [Unreleased]

### Added
- Backup strategies `sqlite_volume` and `volume`. `sqlite_volume` runs a named snapshot builtin (`gitea` or `vaultwarden`) and tars `mount`, leaving out `tar.exclude`. `volume` tars `mount` while the container runs, so a file written during the tar can be torn. Mounts and excludes come from the template. The snapshot scripts stay in Go. The shipped Gitea and Vaultwarden templates use `sqlite_volume`, and MinIO uses `volume`. A new MinIO instance starts with **Allows backups** on. One that already exists stays off until the switch is turned on. `manifest.json` records `mount` and `snapshot`, and `goforge backup restore-service` uses them. `gitea` and `vaultwarden` still work as strategy names. See `docs/reference/service-templates.md#backup-strategy`
- Service templates declare `backup.strategy` (`postgres`, `sqlite_volume`, or `volume`; `gitea` and `vaultwarden` are still accepted as aliases). The nightly run and `goforge backup run` read it from the catalog instead of switching on the template name, and reload template files at the start of the run. A template with no strategy, or a strategy the runner does not know, is skipped and has no **Allows backups** switch. The template name can differ from the strategy. The shipped Postgres, Gitea, Vaultwarden, and MinIO templates set the field. An unknown strategy is logged when the template loads and does not stop the template from deploying. See `docs/reference/service-templates.md#backup-strategy`
- **Allows backups** on each Postgres, Gitea, Vaultwarden, and MinIO service page. The nightly backup and `goforge backup run` include that instance only when the switch is on and the container is running. Turning it off lists the instance in the run manifest as skipped (`backups disabled for this instance`). Other templates have no switch, and a request to turn backups on for one is refused. The flag is `service_instances.backup_enabled` (migration `032_service_instances_backup_enabled`): existing Postgres, Gitea, and Vaultwarden instances stay on, existing MinIO instances start off, and a new deploy of any of the four starts on. Each change writes `service.set_backup` (`details.backup_enabled`, `details.previous`, `via` = `ui`). `GET /api/v1/services` and `GET /api/v1/services/{id}` return `backup_enabled`. The GoForge database is still in every run. Route `POST /services/{id}/backup`. See `docs/deployment/backup.md#allows-backups`
- Service template ports can route a second public host with `docker.ports[].domain` (a Go template, ports after the first only). GoForge adds a `goforge-svc-<id>-p<port>` Traefik router and service for it and names the service on every router of that container. A value that is not a hostname or repeats the instance Domain is refused before a container is touched. The **MinIO** template uses it: a new optional **Console Domain** field routes that host to the console on 9001 and sets `MINIO_BROWSER_REDIRECT_URL`, so the API host stops redirecting browsers to the unreachable `<domain>:9001`. Existing MinIO instances are unchanged until **Edit configuration** sets Console Domain (which recreates the container). See `docs/guides/services.md#minio` (t1935u)

### Security
- Audit log retention and tamper detection (v0.5.1). Settings → Profile → **Audit log** (admins) sets how long rows are kept: `0` (the default) keeps them forever, otherwise 30 to 3650 days. `GOFORGE_AUDIT_RETENTION_DAYS` is used only until an admin saves the card; a saved row wins and the card shows which one is in effect. A job runs about five minutes after startup and then daily, hard-deletes old rows in batches of 5000: a prefix of the chain, an old suffix sealed after every row still inside the window, and unsealed rows older than the cutoff. The transaction sets `goforge.audit_purge` (any database session can set that flag; the table owner can also `DISABLE TRIGGER`) and, in that same transaction, writes the `audit.retention.purge` row when the chain boundary moves. It also writes one `audit.settings.update` row when the setting changes (`old_days`, `new_days`). A purge that deletes rows records `deleted`, `cutoff`, `through_seq`, `through_hash`, and `purge_mac`. Migration `031_audit_retention_and_seals` adds `audit_settings` and `audit_log_seals`, drops `audit_logs.user_id`'s foreign key so deleting a user cannot rewrite a sealed row (the id stays), and adds triggers that reject `UPDATE`, `DELETE`, and `TRUNCATE` unless `goforge.audit_purge` is `on` for that transaction. Even then, `DELETE` is only allowed for rows older than 30 days, which keeps `FindApproval` replay protection inside the window. Every row older than about five seconds is sealed into an HMAC-SHA256 chain. The key is HKDF-SHA256 of `ENCRYPTION_KEY` with info `goforge-audit-chain-v1` and is not stored. `goforge audit verify [--from-seq N]` exits 0 when the chain is intact and 1 with the first bad seq and reason (`hash mismatch`, `missing row`, `unsealed row older than 5 minutes`, `boundary mismatch`, `boundary without purge`). `boundary without purge` is a stored boundary with no `audit.retention.purge` row whose `purge_mac` is the chain-key HMAC of `through_seq`, `through_hash`, `deleted`, and `cutoff` (`goforge-audit-purge-v1`). A sealed purge row without that MAC does not count: the sealer seals every row. The honest purge writes the MAC in the same transaction as the boundary, so verify does not wait for the seal. `goforge serve` runs the same check about 30 seconds after startup and then daily and logs `audit chain verified head_seq=N head_hash=...`. Each backup `manifest.json` gains `audit_chain_head`. Settings → Activity states the retention rule, and admins also see the last integrity check. Limits, stated on purpose: this detects someone who can write the database but cannot read `ENCRYPTION_KEY`. It does not stop someone with the Docker socket or root on the host, who can read the key and rewrite every anchor. A row deleted in the few seconds before it is sealed leaves no trace. Rows that already existed at upgrade are only proven unchanged since the first seal. A separate insert-only database role is not in this release. See `docs/guides/activity.md`

## [0.5.0] - 2026-11-02

### Fixed
- The **MinIO** template image is now `pgsty/silo:{{ .Version }}` (default `latest`) instead of `minio/minio`, which MinIO deleted from Docker Hub, so a MinIO deploy no longer fails with `pull access denied`. `quay.io/minio/minio` was not used because it now refuses anonymous pulls (401). Silo is a community MinIO fork and a drop-in: the command, `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`, `/data` volume, curl health check on `/minio/health/live`, and console on 9001 are unchanged (t1878u)

### Changed
- **Prune System** on the Dashboard gives feedback (t1905u). The button is now an htmx request (`hx-post`, `hx-disable`, `hx-indicator`) behind the same kit confirm: while it runs it is disabled with a spinner and **Pruning…**; when it finishes a success toast names what was freed (`Pruned 3.42 GB: 2 containers, 5 images, 41 build cache records`, or **Nothing to free**) and the **Docker Disk Usage** card re-renders in place without a page reload. A failure is a `RenderError` error toast (**Prune System failed…**, Docker error text only in the log) and the page stays put, instead of a bare text page. `CleanupSystem` now returns a `docker.PruneSummary` built from the `PruneReport`s Docker already returns (same steps, order, and stop-on-first-error); `POST /settings/prune` uses the same toast text, and a plain form POST to `/dashboard/prune` still redirects to `/dashboard`. The Dashboard stats loader now swaps with `outerHTML`, so the loaded stats replace it instead of nesting a second `#dashboard-stats` inside it. See `docs/guides/monitoring.md#system-prune`
- **Prune System** now also prunes unused Docker build cache (t1876u). `CleanupSystem` runs `BuildCachePrune` with `all` after the managed container and image prunes; build cache has no labels, so this step is engine-wide (as the **Build Cache** card already was). Build cache that is neither in use nor shared is counted in a new `DiskUsageInfo.BuildCacheReclaimable` and folded into `ReclaimableSize`, so the button and the **Reclaimable Space** alert are enabled when build cache is the only waste (before, a large build cache with nothing else to free left the button disabled). The alert names the build cache share, and the confirm dialog says build cache is engine-wide. See `docs/guides/monitoring.md#system-prune`

### Security
- Opt-in TOTP two-factor authentication for local password accounts (v0.5.0 S4, t1873u). Settings → Profile → **Two-factor authentication**: re-enter the password, scan the QR code (or type the key), confirm with the first code, and save the 10 recovery codes shown once (migration `030_two_factor`: `user_totp` with the key sealed by `ENCRYPTION_KEY`, `user_recovery_codes` as SHA-256 hashes, `login_challenges` as token hashes). With 2FA on, `POST /auth/login` with the right password answers `303 /auth/2fa` and sets the 5-minute HttpOnly `goforge_2fa` cookie instead of a session; `POST /auth/2fa` takes a 6-digit code (±30 s, each time step once) or a recovery code (each once) and then creates the session. Wrong codes count toward the existing login lockout (`429` with `Retry-After`), and 5 wrong codes end the challenge. Turning it off needs the password and a code. `goforge user reset-2fa <email>` clears it for a locked-out user. New audit actions `user.2fa.enable`, `user.2fa.disable`, `login.2fa_failed`, `user.2fa.reset` (`via` = `cli`, shown with a new **CLI** source on Settings → Activity), and `login` rows carry `second_factor` (`totp` or `recovery_code`). Not forced for anyone. Sign in with GitHub does not ask for a GoForge code (it relies on GitHub's 2FA, and links a same-email local account as before), and API tokens and `/mcp` are unaffected. TOTP only; no WebAuthn
- The remaining audit gaps are closed (v0.5.0 S3, t1870u). Settings → Git sources add and remove write `git_source.create` and `git_source.delete` (name, type, `has_access_token`, `has_api_url`; never the token, SSH key, or API URL). A Profile save writes `user.profile.update` with `changed` (`["email"]` or empty) and `old_email_domain` and `new_email_domain`, never the full address. Each deployment a signed GitHub, Gitea, or GitLab push starts writes `deployment.trigger` with `via` = `webhook`, `provider`, `branch`, `commit`, `repository`, `project_id`, and `environment_id`, owned by the project owner, and the queued run's `deployment.run.*` row links back through `details.audit_id` (a queue failure writes `deployment.trigger.failed`). Settings → Activity has a **Webhook** source badge and filter (`?source=webhook`); webhook rows no longer count as `UI`. There is still no audit retention setting (nothing is purged) and no tamper protection; `SECURITY.md` lists both as open. See `.cursor/skills/verify-goforge/features/audit-activity.md`
- Changing the password ends the account's other sessions. A successful `PUT /settings/password` deletes every session of the account except the one that made the change (`SessionRepository.DeleteByUserIDExcept`), so a stolen session cookie stops working once the password is changed. Settings → Profile has a new **Sessions** card with **Sign out other sessions** (`POST /settings/sessions/revoke-others`), which does the same without a password change. Both write an audit row, `user.password.change` or `user.sessions.revoke`, with `sessions_revoked` (the number of sessions ended) and `via` = `ui`, never the password or a hash. API tokens are not revoked. See `.cursor/skills/verify-goforge/features/session-revoke.md` (v0.5.0 S2, t1861u)
- `/health/ready` no longer returns database or Docker error text (HEALTH-READY-PUBLIC). The route stays public and keeps its status codes (`200` ready, `503` not ready) and its `checks` keys, but each value is now only `ok`, `unavailable`, or `not_configured` for every caller. The error behind `unavailable` is logged server side as a `readiness check failed` warning with `check` and `error` fields. `verify.sh` still reads `"database":"ok"`. New verification file `.cursor/skills/verify-goforge/features/health-ready.md` (t1858u)

## [0.3.0] - 2026-11-02

### Added
- Optional **Error reporting (Sentry)** for the GoForge control plane: Settings → Profile gains an admin-only **Error reporting (Sentry)** card with a DSN field, an environment (default `production`, `development` in dev mode), **Send test event**, and **Save error reporting**. With a DSN, a panic in a web or `/api/v1` handler, a panic in an in-process `/mcp` tool call, and every handled `5xx` page (`RenderError`) is sent to Sentry with its chi route pattern, method, and status as tags (the request still gets its `500`). Blank means off; a save or **Remove the stored DSN** takes effect at once without a restart. The DSN is sealed with `ENCRYPTION_KEY` in `error_reporting_settings` (migration `029_error_reporting_settings`), never shown again (the card shows only scheme, host, and project), and must be `https://` (`http://` only on a loopback host) without a secret key. `SENTRY_DSN` is read only while no settings are saved. Events carry no cookies, `Authorization`, CSRF or API-key headers, query strings, request bodies, client IPs, or user details, and messages go through the notification redactor. Tracing is off. Saves are audited as `error_reporting.settings.update` with changed field names only. Routes `PUT /settings/error-reporting` and `POST /settings/error-reporting/test`. See `docs/configuration/index.md#error-reporting-sentry` (t1770u)
- One-click GIS templates: **GeoLibre** (`templates/geolibre.yaml`, `ghcr.io/opengeos/geolibre:v3.6.0`, port 80, `data` volume at `/data`) with Share and the Project Gallery off (`GEOLIBRE_SHARE_URL=off`), the Python sidecar off by default (`GEOLIBRE_DISABLE_SIDECAR=1`, **Python Processing Sidecar** select to turn it on), a GeoLens URL field (default `off`), and optional shared Basic Auth (set only when both user and password are filled); and **RustGIS** (`templates/rustgis.yaml`, `ghcr.io/opengeos/rustgis:0.5.0`, port 8080, no config or volume). Restart stays allowed. - Container health watch: while notifications are on, serve inspects tracked containers once a minute and sends `container.unhealthy` or `container.exited` (also `dead` or `restarting`) for one that should be running: its row is `running`, it is older than 2 minutes, and its service (if any) is `running`. One alert per episode, at most one per container per 30 minutes (`TestHealthWatch*`, t1654u slice 12)
- `goforge backup restore-service <run key> <instance id>` restores one Postgres, Gitea, or Vaultwarden service's data volume from a backup run. Dry run by default; `--yes` asks for the run key (or `--confirm=<run key>`), takes the backup lock, checks every artifact's size and SHA-256 before stopping anything, stops the service, moves the current volume contents to `<volume>/.goforge-pre-restore-<UTC time>/` (kept, never deleted), extracts the backup with its owners in a no-network helper from the service's own image, puts the SQLite snapshot at the database path with its directory's owner, starts the service, and waits for its health check. For Postgres it builds a fresh cluster with `initdb` as the data directory's owner and the service's `POSTGRES_USER`, carries over `postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf`, and `pg_ident.conf`, loads `roles.sql` and each dump (`pg_restore --create --exit-on-error`) on a socket-only temporary server, then moves it into `/var/lib/postgresql/data` (t1650u). Drilled by `TestIntegration_RestoreService` on throwaway Gitea and Vaultwarden and `TestIntegration_RestoreServicePostgres` on a throwaway `postgres:17` (round trip plus a bad-dump rollback); the runbook in `docs/deployment/backup.md` is updated

### Fixed
- Redeploy cleanup read only the ten newest deployments of the environment (`LIMIT 10`), so an older deployment still running behind more than ten newer failed or canceled deploys was never retired and its container ran beside the new one. Cleanup now reads every running deployment of the environment (`TestRetireSupersededPastTenNewerFailures`). `formal/deploy-retire/view.ts` labels a cleanup waiting to retry a failed retire as "retire failed, retry pending" instead of "settled", and its `RetryRetire` step as "cleanup retries the retire"
- Two redeploys of one environment within the 5-minute grace period could leave no container running: the first redeploy's cleanup retired every other running deployment, including the newer one, and the newer one's cleanup then retired the first. Cleanup now retires only deployments older than the newest one whose grace is over (by `created_at`), so the newest container keeps serving and the one before it serves through its successor's grace (`TestReplayBackToBackRedeployKeepsNewest`, `TestRetireSupersededNeverRetiresNewer`; finding F1 in `formal/deploy-retire`)
- When Docker failed both `docker stop` and `docker rm` on the previous container (daemon unreachable), cleanup still marked its row `exited`, so nothing ever retried and the old container kept running beside the new one. The row now stays `running` until the container is removed (a "no such container" error counts as removed), the cleanup retries every 30 s (each pass bounded to 2 min; the 10-minute overall timeout is gone), logs `retire of previous deployment incomplete, will retry`, and after a restart `RecoverPendingRetires` picks it up (`TestReplayDockerErrorsLeaveNoSecondRunning`, `TestCleanupOldDeploymentsRetriesFailedRemove`, `TestCleanupOldDeploymentsKeepsRowRunningWhileDockerDown`; finding F2). The F1/F2 replays no longer need the `formalreplay` build tag, so `make test` runs them; `formal/deploy-retire/check.sh` now expects every rule to hold on all three configs, with new mutants `PreF1RetireNewer` and `PreF2ExitOnError` proving the model still catches both bugs
- A GoForge restart within the 5-minute grace period after a redeploy left the previous deployment's container running beside the new one: the grace timer lived only in memory, so nothing retired it. On startup GoForge now finds each environment whose newest running deployment still has an older running container, waits out what is left of the grace period (from when the new deployment became running), or retires it at once if the grace is over, and logs `recovering pending retire of previous deployment` (`TestRecoverPendingRetiresAfterGraceElapsed`, `TestRecoverPendingRetiresHonorsRemainingGrace`)

### Security
- Deleting a service or a project in the web UI asks for its name in a dialog, and the server checks it: `DELETE /services/{id}` and `DELETE /projects/{id}` without `confirm_name` equal to the exact name answer `400` and remove nothing (t1663u slice 14)
- GoForge refuses to start outside dev mode when `WEBHOOK_SECRET` is empty or only whitespace (`WEBHOOK_SECRET is required`), like `ENCRYPTION_KEY`, `SESSION_SECRET`, and `CSRF_SECRET`. An empty secret let anyone sign a GitHub or Gitea webhook (HMAC with an empty key) or send an empty `X-Gitlab-Token`. Dev mode still generates the secret when it is unset. Installs that already set it are unaffected. `docker-compose.yml` still passes `${WEBHOOK_SECRET:-}` so dev-mode Compose runs without it
- Backup keys saved in Settings → Profile are stored sealed with `ENCRYPTION_KEY` instead of as container environment variables readable with `docker inspect`; after the first-start import, remove every `BACKUP_*` line from your env file (`.env`) and recreate the container (ENV-CREDS). The backup redactor also covers the saved keys
- Client IP for the rate limiter, login lockout, audit log, and API: from a `TRUSTED_PROXIES` peer, GoForge now uses the rightmost `X-Forwarded-For` hop that is not a trusted proxy, then `X-Real-IP`. The leftmost `X-Forwarded-For` entry is client-written and is no longer trusted, so rotating it no longer gets a fresh rate-limit bucket. `TRUSTED_PROXIES` is documented in `.env.example` (XFF-SPOOF, #70)
- `CF-Connecting-IP` is read (before `X-Forwarded-For`) only when `CLOUDFLARE_PROXY_MODE=true`. It is off by default because Traefik forwards the header as the client sent it, so a client that reaches Traefik directly could otherwise pick its own client IP. Tunnel deployments should set `CLOUDFLARE_PROXY_MODE=true` so tunnel users do not share cloudflared's rate-limit bucket (CF-SPOOF, #70)
- Login lockout: 10 failed password logins per client IP, or per account from any IP, within 15 minutes lock that key for 15 minutes; `POST /auth/login` answers `429` with `Retry-After` before checking the password (LOGIN-THROTTLE, #70)
- Security headers on every response: `Content-Security-Policy: frame-ancestors 'none'; base-uri 'self'; object-src 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Strict-Transport-Security: max-age=31536000` on HTTPS (NO-SEC-HEADERS, #70)
- CSRF tokens are HMAC-SHA256 keyed by `CSRF_SECRET` (previously required but unused): session-bound when signed in, signed nonce when signed out. A planted `goforge_csrf` cookie no longer passes. Pages open across the upgrade need one reload (CSRF-SECRET-UNUSED, #70)
- `goforge serve` deletes expired session rows at startup and hourly (SESSION-PURGE, #70)
- Dependency and toolchain bump to clear every reachable `govulncheck` finding: builder image `golang:1.26.10` and `go 1.26.0` in `go.mod` (CI `GO_VERSION` 1.26); go-git v5.19.3, go-billy v5.9.2, golang.org/x/crypto v0.58.0, golang.org/x/net v0.62.0, OpenTelemetry v1.47.0, cloudflare/circl v1.6.5, go-chi/chi v5.3.0. The Docker SDK moves from `github.com/docker/docker` v27.3.1 (GO-2026-4887, GO-2026-4883: no fixed version of that module) to `github.com/moby/moby/client` v0.6.2 and `github.com/moby/moby/api` v1.56.1 (DEPS-VULN, #69)
- Added trusted proxy validation for `X-Forwarded-For` / `X-Real-IP` headers (configurable via `TRUSTED_PROXIES` env var)
- Repo `docker-compose.yml`: the Traefik API and dashboard are off by default (`--api`, `--api.dashboard`, and `--api.insecure` follow `TRAEFIK_DASHBOARD_INSECURE`, default `false`, so `api@internal` does not exist and a label-defined router cannot expose it); the unauthenticated `traefik-dashboard` router (`Host(traefik.${GOFORGE_DOMAIN})`, `web` entrypoint, `api@internal`) is removed; the dashboard port is published on `127.0.0.1:${TRAEFIK_DASHBOARD_PORT:-8081}` instead of `0.0.0.0`. Traefik 80/443 are unchanged (all interfaces, for direct installs); tunnel deployments should bind them to loopback in an override (REPO-COMPOSE-TRAEFIK, #71)
- Pinned images: `cloudflare/cloudflared:2026.6.0` (was `latest`) in Compose, and `alpine:3.24` (was `latest`) for the runtime and `mcp` Dockerfile stages (UNPINNED, partial, #71)
- `SECURITY.md` documents the Docker socket trust model: the read-write socket in the `goforge` container, Traefik's `:ro` socket (which does not limit API calls), and `docker` group membership are root-equivalent on the host; mitigations and the Cloudflare Tunnel + loopback exposure model (DOCKER-SOCK, #71)
